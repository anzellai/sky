**Branch:** `feat/v0.17-fully-typed-codegen`
**Predecessor:** C17a (`b663dc3f`), C17b (`f5570b0d`)
**Status:** C17c flip ATTEMPTED + REVERTED this tick. Captured here so future ticks know the blast radius.

## Attempted change (reverted)

1. `Sky.Type.Constrain.Expression.lookupKernelType`:
   - `Context.background` / `Context.todo` return type changed from
     `TType (Canonical "") "Value" []` to
     `TType (Canonical "") "Context_at_context" []`.
2. `Sky.Build.FfiTypeResolve.goApp`:
   - Qualified-marker arm flipped from
     `let _ = ... in opaqueValue`
     to
     `Can.TType (Canonical "") (bare ++ "_at_" ++ mangle pkg) args`.

## What broke

`examples/13-skyshop` failed with:

```
Variable 'app_' type mismatch:
  App_at_firebase_google_com_go_v4 vs Value

Variable 'listParams' type mismatch:
  Value vs CustomerListParams_at_github_com_stripe_stripe_go_v84
```

## Root cause

The skyshop source calls
`Stripe.customerListParamsSetEmail userEmail p`. Inspection of the
freshly-regenerated `examples/13-skyshop/.skycache/ffi/stripe.kernel.json`
shows `customerListParamsAddExpand`,
`customerListParamsGetListParams`, etc. — but **no entry for
`customerListParamsSetEmail`**. The inspector skipped it (likely
filtered by `shouldSkipFn` for a parameter shape that can't be
faithfully rendered).

So Sky resolves `customerListParamsSetEmail` via the legacy
`Can.VarKernel` path (no FtyAst → no qualified marker → falls
back to `Value`). Meanwhile `Customer.list` IS in the kernel.json
with the qualified marker, so its parameter slot is
`CustomerListParams_at_...`. Mismatch.

Same shape for `App_at_firebase_google_com_go_v4 vs Value` — one
side resolves via the qualified inspector path, the other doesn't.

## Why C17b was safe

C17b parses and propagates the qualified marker, but the resolver
collapses to `Value` at the final step. So BOTH symmetric and
asymmetric FFI surfaces emit `Value`, and HM treats them
identically. The qualified info is dormant but present.

C17c's flip makes the resolver act on the qualified info. Symmetric
surfaces gain proper distinctness; asymmetric surfaces break.

## Required work for true C17c

Pick exactly one approach:

### Option A — Inspector completeness

Audit `tools/sky-ffi-inspect/main.go` `shouldSkipFn` to expand
inspector coverage of every Sky-reachable FFI symbol. Verify
`customerListParamsSetEmail` (and every other "missing" symbol)
either:
- Surfaces in the kernel.json, OR
- Gets explicitly rejected in canonicaliser with a clear error
  (so Sky code can't silently fall back to a Value-typed
  unknown).

This is the principled fix but high-effort.

### Option B — Resolver bridges Value ↔ qualified

In `FfiTypeResolve.goApp`, when emitting a qualified type, also
register an HM unification axiom `Value ⊆ qualified`. So a value
typed as `Value` flows transparently into a qualified-typed slot
and vice versa. The runtime wrapper still does the actual
`.(*pkg.X)` cast.

This preserves existing behaviour for asymmetric surfaces while
gaining distinctness for symmetric ones. Lower-risk close.

Requires extending Sky.Type.Solve's unification with a per-pair
bridge rule — non-trivial but isolated.

### Option C — Migrate all hand-coded sigs to BOTH Value and qualified

Emit two HM bindings per hand-coded kernel — `Context.background`
returns `Value`, AND `Context.background` ALSO available under
the qualified name. Caller resolves via best-match. Most
complex; not recommended.
