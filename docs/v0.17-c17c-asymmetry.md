# C17c asymmetry discovery — Cause G next-step blocker

**Branch:** `feat/v0.17-fully-typed-codegen`
**Predecessor:** C17a (`b663dc3f`), C17b (`f5570b0d`)
**Status:** C17c flip ATTEMPTED + REVERTED this tick. Captured here so future ticks know the blast radius.

## Attempted change (reverted)

1. `Sky.Type.Constrain.Expression.lookupKernelType`:
   - `Context.background` / `Context.todo` return type changed from
     `TType (Canonical "") "Value" []` to
     `TType (Canonical "") "Context_at_context" []`.
2. `Sky.Build.FfiTypeResolve.goApp`:
   - Qualified-marker arm flipped from
     `let _ = ... in opaqueValue`
     to
     `Can.TType (Canonical "") (bare ++ "_at_" ++ mangle pkg) args`.

## What broke

`examples/13-skyshop` failed with:

```
Variable 'app_' type mismatch:
  App_at_firebase_google_com_go_v4 vs Value

Variable 'listParams' type mismatch:
  Value vs CustomerListParams_at_github_com_stripe_stripe_go_v84
```

## Root cause

The skyshop source calls
`Stripe.customerListParamsSetEmail userEmail p`. Inspection of the
freshly-regenerated `examples/13-skyshop/.skycache/ffi/stripe.kernel.json`
shows `customerListParamsAddExpand`,
`customerListParamsGetListParams`, etc. — but **no entry for
`customerListParamsSetEmail`**. The inspector skipped it (likely
filtered by `shouldSkipFn` for a parameter shape that can't be
faithfully rendered).

So Sky resolves `customerListParamsSetEmail` via the legacy
`Can.VarKernel` path (no FtyAst → no qualified marker → falls
back to `Value`). Meanwhile `Customer.list` IS in the kernel.json
with the qualified marker, so its parameter slot is
`CustomerListParams_at_...`. Mismatch.

Same shape for `App_at_firebase_google_com_go_v4 vs Value` — one
side resolves via the qualified inspector path, the other doesn't.

## Why C17b was safe

C17b parses and propagates the qualified marker, but the resolver
collapses to `Value` at the final step. So BOTH symmetric and
asymmetric FFI surfaces emit `Value`, and HM treats them
identically. The qualified info is dormant but present.

C17c's flip makes the resolver act on the qualified info. Symmetric
surfaces gain proper distinctness; asymmetric surfaces break.

## Required work for true C17c

Pick exactly one approach:

### Option A — Inspector completeness

Audit `tools/sky-ffi-inspect/main.go` `shouldSkipFn` to expand
inspector coverage of every Sky-reachable FFI symbol. Verify
`customerListParamsSetEmail` (and every other "missing" symbol)
either:
- Surfaces in the kernel.json, OR
- Gets explicitly rejected in canonicaliser with a clear error
  (so Sky code can't silently fall back to a Value-typed
  unknown).

This is the principled fix but high-effort.

### Option B — Resolver bridges Value ↔ qualified

In `FfiTypeResolve.goApp`, when emitting a qualified type, also
register an HM unification axiom `Value ⊆ qualified`. So a value
typed as `Value` flows transparently into a qualified-typed slot
and vice versa. The runtime wrapper still does the actual
`.(*pkg.X)` cast.

This preserves existing behaviour for asymmetric surfaces while
gaining distinctness for symmetric ones. Lower-risk close.

Requires extending Sky.Type.Solve's unification with a per-pair
bridge rule — non-trivial but isolated.

### Option C — Migrate all hand-coded sigs to BOTH Value and qualified

Emit two HM bindings per hand-coded kernel — `Context.background`
returns `Value`, AND `Context.background` ALSO available under
the qualified name. Caller resolves via best-match. Most
complex; not recommended.

## 2026-06-13 Update — Inspector audit landed, three more issues surfaced

Commit `7f0f8dfb` (the user-directed inspector audit) closed
Option A's headline gap: receiver positions now route through
`paramFor`, so every FFI surface emits the qualified marker in
every position (receiver, param, result). Verified on
`customerListParamsSetEmail` which now emits:
```
String -> CustomerListParams@github.com/stripe/stripe-go/v84
       -> Result Error CustomerListParams@github.com/stripe/stripe-go/v84
```

With that inspector fix in place I re-attempted the resolver flip
in `FfiTypeResolve.goApp` + migrated `Context.background` /
`Context.todo` to the qualified form. Example sweep then surfaced
three NEW distinct issues:

1. **Go interface widening** — Fyne's `Label` implements
   `CanvasObject`; pre-flip both unified at `Value` by accident.
   Post-flip they're distinct qualified types and the conversion
   site fails:
   ```
   display : Label_at_fyne_io_fyne_v2_widget
          vs CanvasObject_at_fyne_io_fyne_v2
   ```
   Sky has no equivalent of Go's interface satisfaction. Either
   the resolver needs Option B's Value↔qualified bridge OR Sky
   gains explicit interface-widening helpers.

2. **More hand-coded sigs returning Value** — `net/http`'s
   `Handler` is referenced from a place that emits Value (likely
   another `lookupKernelType` arm). Need a sweep through every
   hand-coded sig that returns or accepts an opaque FFI type.

3. **Cross-module FFI composition** — Stripe surfaces additional
   sites where the unification fails even after Context. Likely
   more hand-coded ops + the Go-interface-widening case.

Both the resolver flip and the Context migration were reverted to
keep example sweep GREEN. The inspector audit stays shipped — it's
strictly additive and safe.

**Updated recommendation**: C17c full close needs the
Value↔qualified bridge in `Sky.Type.Solve` (Option B) as a
prerequisite, not as an alternative. Inspector audit alone isn't
sufficient because:
- (1) is a Go-level structural relation Sky doesn't model
- (2) is a long-tail audit of hand-coded sigs
- (3) compounds (1)+(2)

The bridge naturally subsumes ALL three cases by letting `Value`
flow into any qualified slot transparently.

## 2026-06-13 third attempt — bridge + resolver flip, blocked on codegen flatten + Go interface satisfaction

Added Value ↔ qualified bridge to `Sky.Type.Unify` (App1 arm) and
flipped resolver in `FfiTypeResolve.goApp` to emit qualified type
as `Bare_at_pkg`.  Example sweep dropped 26/26 → 23/26:

- `11-fyne-stopwatch`: `Label_at_fyne_io_fyne_v2_widget` vs
  `CanvasObject_at_fyne_io_fyne_v2` — qualified↔qualified pair,
  bridge only covers Value↔qualified.  Go interface satisfaction
  Sky has no equivalent of.
- `05-mux-server`: `undefined: Router_at_github_com_gorilla_mux`
  at `go build` — qualified types leak into Go codegen as
  identifiers but the runtime has no such Go type defined.
- `13-skyshop`: same `undefined: <Qualified>_at_...` family.

Both reverted; sweep restored to 26/26.  The bridge approach
needs TWO paired fixes Sky doesn't currently have:

1. **Codegen flatten** — every `X_at_pkg` token must become `any`
   (or pkg.X via inspector-provided runtime wrapper) at Go
   emission.  Currently the `_at_` form is passed through to
   `go build` raw.
2. **Interface satisfaction modeling** — when callee expects
   `CanvasObject_at_fyne` and caller has `Label_at_fyne_widget`,
   HM must consult Go's interface relation.  Options: kernel.json
   interface-list registry; generic "FFI-opaque widen" rule;
   asymmetric drop (qualified for return only).

Architectural design for these prerequisites is the real C17c
delivery.  Cause G stays at C17a + C17b infrastructure layer
with this third attempt documented as the next blocker.
