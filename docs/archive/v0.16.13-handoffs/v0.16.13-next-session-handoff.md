## Why the previous attempts failed — IMPORTANT

ALL approaches that tried to "fix" the IORef-based scope readers
(`enclosingTypeParamInScope`) by routing them through `LowerCtx`
parameters or `snapshotCallerCtx ()` snapshots **FAIL** due to GHC's
CAF caching:

| Attempt | Failure mode |
|---|---|
| Commit 3 — `eraseTypeParamsExceptScope enclosingTypeParamInScope` at coerceArg/coerceToFieldType fallback | Closes Widget. **Breaks** 8 examples (06-json, 12-skyvote, 13-skyshop, 17-skymon, 18-job-queue, 19-skyforum, 27-multi-session-chat, 31-webview-stopwatch-ui) with `undefined: T1` errors at non-generic lambda positions. CAF cache returns True for "T1" inside non-generic bodies. |
| Commit 2 — LowerCtx threading through `coerceCallArgsAt` with `Set.member t (LC._lc_enclosingTypeParams ctx)` and `snapshotCallerCtx ()` at call sites | Same regression class. `snapshotCallerCtx ()`'s thunk is CAF-shared across call sites; first generic-fn snapshot is cached and reused in non-generic contexts. |
| Phase A — `Solve.lookupSolvedRegion` fallback in `inferExprType (Can.VarLocal)` | Doesn't close skydeploy because the name lookup succeeds first (just returns a TVar that isn't chased). |

The fundamental problem: **GHC shares CAF thunks across call sites**
where the application looks identical (`enclosingTypeParamInScope "T1"`,
`snapshotCallerCtx ()`, etc.). NOINLINE prevents the body from
inlining but doesn't prevent thunk-sharing of the APPLICATION.

## The architectural principle (user's guidance)

> "Use the tracking of Sky code as HM has the guarantee of usage —
> so types are fully known if used or called. We need to just defer
> the Go code gen when the actual usage is in Sky code, otherwise
> staying generic is actually fine."

**Translation**: When HM tells us source's parametric record type
matches the callee's expected param type (both `Cfg_R[...]` with
same base), emit `editorBody(cfg)` RAW. Go's call-site generic
inference pins T1 from cfg's static type. No cast needed.

The parametric-alias shortcircuit at `coerceArg:9742-9745` (path b)
IS this design. It uses `aliasBaseFromCanExpr` to recover the alias
base name from the source's HM-solved type. The bug is path (b)
**doesn't fire reliably** for cfg refs in nested-IIFE bodies.

## Why path (b) misses — diagnosis

`aliasBaseFromCanExpr (Can.VarLocal "cfg")` at line 10123:

```haskell
case inferExprType solved src of
    Just (T.TAlias homeMod aliasName _ _) ->
        let prefix = ...
            qualified = prefix ++ aliasName
            isRec     = Set.member aliasName _cg_recordAliases
            isQualRec = Set.member qualified _cg_recordAliases
        in if isRec then Just aliasName
           else if isQualRec then Just qualified
           else Nothing
    _ -> Nothing
```

For skydeploy's Editor.view body's `cfg`:
- `inferExprType solved (Can.VarLocal "cfg")` →
  `Solve.lookupSolvedVar "cfg"` may return a `T.TVar` (unbound
  substitution) instead of `T.TAlias`. Pattern match fails.
- Even if T.TAlias matches, `_cg_recordAliases` membership may
  fail if Editor.Cfg's registration is qualified differently.

## Critical lessons learned (apply to next session)

1. **TEST EVERY CHANGE WITH FULL SWEEP**. Both Widget AND a non-
   generic example (e.g. 06-json) MUST build cleanly before
   declaring a fix works. The Widget-only repro is misleading.
2. **CAF caching defeats IORef-based scope checks**. Don't try
   variants of the same approach. Use HM-based logic (the path b
   shortcircuit) instead.
3. **HM is authoritative**. The user's principle says: when HM
   guarantees the type, defer codegen / skip the cast. Don't try
   to fix the erasure logic — bypass it entirely via the shortcircuit.
4. **Phase 4 ctx threading is NOT the right fix**. It would just
   move the CAF problem from one place to another.
