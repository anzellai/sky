## Sub-PR decomposition

### PR-21a — Codegen flatten (1 session, low risk)

**Problem.** Today the qualified marker `Name@pkgPath` arrives at
`solvedTypeToGo` as a `Can.TType (Canonical "") name args` value
where `name` still contains the `_at_pkg` token (post-mangle).
`solvedTypeToGo` emits the bare identifier verbatim, producing
Go code like `undefined: Router_at_github_com_gorilla_mux` at
`go build`.

**Fix.** In `solvedTypeToGo`'s `T.TType home name args` arm,
when `name` matches the `(.+)_at_(.+)` mangled pattern, emit
`any` (the safety-net Go type).  Optionally consult `pkgAlias`
to emit the canonical Go import alias + type (`mux.Router`); for
this PR we emit `any` and defer the alias path to a follow-up.

**Implementation outline.**

1. Add a pure `splitGoMangledQualified :: String -> Maybe (String, String)`
   helper in `Sky.Build.Compile` (mirrors `splitQualified` in
   `FfiTypeResolve.hs` but on the post-mangle `_at_` form).
2. **Five renderer sites need the short-circuit** (verified
   2026-06-15 via grep of `T.Type -> String` signatures):
   - `safeReturnTypeFullBounded` (~line 6335)
   - `safeReturnTypeBootstrap` (~line 6768)
   - `safeReturnTypePureBounded` (~line 7973)
   - `solvedTypeToGoPreserveTVars` (~line 16328)
   - `solvedTypeToGoBounded` (~line 16533)
3. In each, add the arm BEFORE the catch-all
   `T.TType home name typeArgs` arm:
   ```haskell
   T.TType _ name _
       | Just _ <- splitGoMangledQualified name -> "any"
   ```
4. The five sites currently share the same general dispatch
   pattern; the helper is identical at each.  Consider
   collapsing the five renderers post-PR-21a (out of scope —
   tracked as PR-22 in the master plan).

**Helper specification (adversarial-grilled).**

```haskell
splitGoMangledQualified :: String -> Maybe (String, String)
splitGoMangledQualified s = go s ""
  where
    -- Scan for `_at_` whose prefix matches `[A-Z][A-Za-z0-9]*`
    -- (Go-style type identifier, no underscores) and suffix
    -- matches `[a-z0-9_]+` (mangled Go package path).  The
    -- prefix-no-underscore rule keeps Sky-side module-prefixed
    -- identifiers (`Std_Html_Html`) outside the qualified-
    -- mangled pattern.  No false positives on any Sky internal
    -- identifier.
    go ('_' : 'a' : 't' : '_' : suffix) acc
        | not (null acc)
        , let bare = reverse acc
        , isUpper (head bare)
        , all (\c -> isAlpha c || isDigit c) bare
        , not (null suffix)
        , all (\c -> isLower c || isDigit c || c == '_') suffix
        = Just (bare, suffix)
    go (c : rest) acc = go rest (c : acc)
    go [] _ = Nothing
```

**Empirical gate.**

* `scripts/cabal-test.sh` — green.
* `scripts/example-sweep.sh --build-only` — 26/26 (today's
  behaviour: `Value` always resolves to `rt.SkyValue`; this PR
  changes the post-mangle qualified form to `any` which is what
  resolves at runtime via `rt.Coerce`).
* `scripts/verify-ui-showcase.sh` — green.
* New regression: `Sky.Build.CodegenFlattenSpec` with a fixture
  whose canonical type carries `Router_at_github_com_gorilla_mux`
  and asserts the emitted Go contains `any` not `Router_at_...`.

**Adversarial grill.**

* Q: Does emitting `any` widen the HM type incorrectly?
  - No.  The flatten happens at codegen lowering AFTER HM has
    settled.  The Sky-side type is still `Router_at_github_com_gorilla_mux`
    in the HM solver, just rendered as `any` in Go.  Sky-level
    distinctness preserved.
* Q: What about `[]Router_at_pkg`?  Does the list-arm fire first?
  - Yes — `T.TType _ "List" [elem]` matches first.  The arm
    recursively calls `rec elem` which then short-circuits.
    Output: `[]any` (already what Sky emits for opaque list
    elements).  No regression.
* Q: What if the qualified marker leaks INTO a generic parameter
  position (e.g. `Cfg_R[Router_at_pkg]`)?
  - The generic-arg position also routes through `rec`, so the
    inner `Router_at_pkg` flattens to `any` first.  Output:
    `Cfg_R[any]`.  Valid Go.
* Q: What if `splitGoMangledQualified` mis-matches a legitimate
  Sky identifier containing `_at_`?
  - Sky-side identifiers never contain `_at_` because canonicaliser
    rejects `@` in identifiers AND `_at_` only enters via the FFI
    inspector's mangle.  Mitigation: anchor the regex on the
    `_at_` separator + require the suffix to be a valid Go
    package-path-mangle (all lowercase + underscores + digits).

**Failure mode.** If example sweep drops below 26/26, the
short-circuit is too eager.  Bisect by inspecting which example
flips.  Most likely cause: an FFI surface where the qualified
form does carry semantic distinctness Sky's downstream codegen
relies on.  Revert + add an opt-out env var, NEVER widen the
short-circuit.

### PR-21b — Interface satisfaction via implements registry (2 sessions, medium risk)

**Problem.** Fyne's `Label` Go type implements the `CanvasObject`
Go interface.  Sky has no equivalent of Go's structural interface
satisfaction.  When `container.NewVBox(label)` expects
`CanvasObject` and `label : Label`, Sky-level HM rejects the
unification.

**Fix.** Consume the `implements` registry from `kernel.json` at
HM-solver setup time.  Add a Sky.Type.Unify axiom: when unifying
`Label_at_widget` with `CanvasObject_at_fyne`, consult
`implements[Label_at_widget]`; if the target interface is in the
list, allow the unification (treat as identity).

**Implementation outline.**

1. Plumb the `implements` registry from `kernel.json` through
   `Sky.Build.FfiKernel`'s loader into `Sky.Type.Solve`'s State.
   Touch points: `FfiKernel.loadKernel`,
   `Solve._stImplementsMap :: Map String (Set String)`.
2. In `Sky.Type.Unify`'s App1 arm, when both sides are
   `TType _ name1 []` / `TType _ name2 []` and one is qualified-
   mangled, consult `_stImplementsMap`.  If `name1` implements
   `name2` (or vice versa), succeed with no substitution.
3. Document the asymmetry: `A` implements `I` is one-way (a value
   of type `I` is NOT necessarily of type `A`).  HM treats this
   as `A <: I` only — Sky surfaces it as an explicit `Ffi.widen`
   helper when the reverse direction is needed.

**Empirical gate.**

* `11-fyne-stopwatch` — must build cleanly after the unify rule
  is in place.  Today it builds because both sides resolve to
  `Value` and unify by accident; PR-21b makes the resolution
  principled.
* `scripts/example-sweep.sh` — 26/26 unchanged.
* New regression: `Sky.Type.Solve.InterfaceSatisfactionSpec`
  with a fixture whose kernel.json carries
  `implements: {"Label@widget": ["CanvasObject@fyne"]}` and
  asserts unification succeeds where it would have failed pre-
  PR-21b.

**Adversarial grill.**

* Q: Does the bridge break principal types (abort trigger #4)?
  - The bridge is one-way: `A <: I` not `I <: A`.  Principal
    types are preserved because the unify rule only widens, never
    narrows.  But: a call site that passes a `Label` where a
    `CanvasObject` is expected and the callee internally
    forwards to a `Button` callback (also satisfies
    `CanvasObject`) would unify `Label` with `Button` via the
    common `CanvasObject` supertype.  WRONG.  Mitigation: the
    unify rule must produce `CanvasObject` as the unifier, not
    `Label`.  Both sides widen to the interface, NOT collapse to
    one concrete.
* Q: How does same-module polymorphic re-instantiation interact?
  - Polymorphic re-instantiation alpha-renames TVars per call
    site.  The interface-satisfaction rule fires AFTER the alpha-
    rename, on the concrete instances.  No interaction.
* Q: What happens when `implements` is unavailable (older
  kernel.json)?
  - Default to empty map.  Unification falls back to the legacy
    `Value` collapse via the resolver.  No regression.
* Q: Cyclic interface implements?
  - Go's type system rejects cyclic interface definitions at
    `go build`.  Sky inherits the guarantee.  But: defensive
    coding — bound the lookup walk at 8 levels and bail to
    failure if exceeded.

**Failure mode.** If `11-fyne-stopwatch` fails post-PR-21b, the
implements map is missing the relevant entry — re-run the
inspector with verbose logging and verify `kernel.json` carries
the expected pairs.

### PR-21c — Resolver flip + Value-bridge enable (1 session, low risk)

**Problem.** Sky.Type.Unify already has a `Value` ↔ qualified
bridge from the 2026-06-13 third attempt (reverted).  The
resolver in `FfiTypeResolve.goApp` still falls back to
`opaqueValue` even when the qualified marker is present.  With
PR-21a + PR-21b in place, the resolver flip is safe.

**Fix.** In `Sky.Build.FfiTypeResolve.goApp`'s `Just (bareName,
pkgPath) <- splitQualified name` arm, emit:

```haskell
Can.TType (Canonical "") (bareName ++ "_at_" ++ mangleGoIdent pkgPath) args
```

Concurrently re-enable the `Sky.Type.Unify` Value ↔ qualified
bridge that was reverted (commit ref TBD).

**Empirical gate.** 26/26 sweep.

## Why this isn't a "stop midway" — it's the architecture

Per the v0.17 mandate (no-midway-stop + per-commit-grill), PR-21
decomposes into shippable sub-PRs precisely because the
architectural risk is too high for a single-iteration close.
The c17c-asymmetry doc + 2026-06-13 update + this design doc
together form the de-risked path.  Each sub-PR has its own
empirical gate; if any sub-PR can't ship clean, the failure is
isolated and the prior sub-PRs stay shipped.
