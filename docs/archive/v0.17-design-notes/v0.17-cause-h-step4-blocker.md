# Cause H Step 4 — tuple gate widening blocker (2026-06-13)

**Branch:** `feat/v0.17-fully-typed-codegen`
**Predecessors:** Step 2a–e (recursion guards on six renderers), Step 2f
(bounded `substituteTVarsToGo`).

## What was attempted

Widen the typed-tuple emission gate at **all** six tuple-emission
sites from a hand-coded primitive-only whitelist
(`isPrimitive ∈ {"string", "int", "int32", "int64", "float32",
"float64", "bool", "byte", "rune", "[]byte"}`) to a structural
`isEmittableGoType s && not (containsGenericTypeParam s)` check
sharing the helper `isTypedTupleElement`.

Goal: tuples of richer concrete shapes — `(Int, List Int)`,
`(Foo_R, Bar_R)`, `(Int, rt.SkyMaybe[String])` — emit as `rt.T2[A, B]`
instead of falling back to the boundary-uncertain alias
`rt.SkyTuple2 = T2[any, any]`. This is the actual Cause-H semantic
close.

## What broke

`probe-C-stdui-msg-typed` regressed to `<<loop>>` at the Go-
generation stage:

```
HM infer (deps): 686 functions typed -- Generating Go sky: <<loop>>
```

`<<loop>>` is GHC's blackhole — a thunk's evaluation requires its
own value (a cyclic dependency), not unbounded recursion. The
recursion guards added in Steps 2a–f cap depth at 64 + visited-set,
so plain infinite recursion is impossible. The widened gate triggers
a **different** code path — likely a downstream consumer that
parses the wider gate's typed-tuple string and re-feeds it through
the type system via `inferTypeFromGoString` / `parseTupleTypeArgs`,
creating a cycle that the renderer guards don't observe.

Reverting **only** `substituteTVarsToGo`'s widening (the
parametric-context renderer) did NOT clear the regression —
the loop is independent of which of the six sites carries it,
which suggests the cycle is at the consumer side, not the renderer.

## Why the recursion guards alone aren't enough

Recursion guards prevent a single renderer from looping into itself.
They do NOT prevent a cycle that goes:

```
solvedTypeToGo → widened gate accepts rt.SkyCmd_T[Msg]
                       → emitTypedTuple2 parses rt.T2[…]
                       → exprToGoExpectGo with target "rt.SkyCmd_T[Msg]"
                              → inferTypeFromGoString parses string back to T.Type
                              → lookupRegionType or solver re-asks the type
                                     → original solvedTypeToGo call (cycle)
```

This is **not** an in-renderer cycle. It's a cycle through the
**value-side lowerer + type inference** because the wider gate
makes the Go-type string structurally complex enough to motivate
a re-parse cycle that the previous primitive-only string never
triggered.

## What's actually needed

The full Cause-H close needs **Strategy C** — the GoType ADT
migration:

1. Replace the legacy String-typed Go renderer outputs with the
   typed `GoType` ADT introduced in v0.17 C1.
2. Type-side recursion is then structurally bounded by the ADT's
   own constructors; cycle detection happens at one place
   (`renderGoType`) instead of seven sibling string functions.
3. Value-side lowerers (`emitTypedTuple2`, etc.) consume `GoType`
   directly instead of parsing strings back via
   `parseTupleTypeArgs` / `inferTypeFromGoString`. No round-trip,
   no cycle surface.

This is the multi-week Strategy C track. Estimated 8–12 PRs to
migrate every consumer of the String renderers.

## What's shipping in this batch

* Step 2a–e: recursion guards on the five legacy String renderers
  (`solvedTypeToGo`, `safeReturnTypeFull`, `safeReturnTypeBootstrap`,
  `typeStrWithAliasesReg`, `safeReturnTypePure`,
  `solvedTypeToGoPreserveTVars`).
* Step 2f: bounded `substituteTVarsToGo` (sixth/seventh renderer)
  with the same fuel + visited-set shape.
* `isTypedTupleElement` helper retained but **unused** — it's the
  drop-in gate for the Step-4 widening when Strategy C makes the
  widening safe.

These changes are byte-identical for non-pathological types and
strictly reduce the surface area of the `<<loop>>` blackhole
class — pathological self-referential parametric record aliases
now return `"any"` instead of infinite-looping at depth.

## 2026-06-13 — Strategy C PRs 1–3 shipped; PR 4 attempted + reverted (again)

After Strategy C PRs 1-3 landed (`GoTuple` constructor + structural
`goTypeArgs` accessor + `solvedTypeToGoTyped` sibling +
`tupleElementSlots` replacing `parseTupleTypeArgs`), I retried the
widening at the renderer-gate level.  Two configurations
attempted:

* **Single-site widen** at `solvedTypeToGo` only (5/6 sites stay
  primitive) → probe-sweep 9/9 GREEN (probe-C-stdui-msg-typed
  passes!) BUT example-sweep 25/26 — `examples/26-ui-showcase`
  fails Go build with the classic asymmetry:
  ```
  cannot use []rt.T2[int, []Std_Ui_Transform_Prop]{…}
      (value of type []rt.T2[int, []Std_Ui_Transform_Prop])
      as []rt.SkyTuple2 value in struct literal
  ```
  `solvedTypeToGo` emits the typed `rt.T2[…]` slot but a
  sibling renderer (likely `typeStrWithAliasesReg` or
  `safeReturnTypeFull`) still emits `rt.SkyTuple2` for the
  matching consumer position.  The two strings represent the
  same Go type via the runtime alias `type SkyTuple2 =
  T2[any, any]`, but Go's type checker treats them as
  distinct because `T2[int, []…]` and `T2[any, any]` are
  different generic instantiations of the same type.

* **Five-site widen** (`solvedTypeToGo` + four bounded sibling
  renderers, `substituteTVarsToGo` stays primitive) →
  probe-sweep 8/9 — probe-C-stdui-msg-typed `<<loop>>`s again,
  same blackhole as the pre-PR-3 attempt.

PR 3's structural `tupleElementSlots` only closes the
**renderer-side** seam — the lossy `parseTupleTypeArgs` is gone.
But the **value-side** seam through `inferTypeFromGoString`
(at Compile.hs:8064) is unchanged, and the wider gate sends
richer types through it.  `inferTypeFromGoString` returns
`T.TVar "_"` for any non-primitive shape, then downstream
consumers re-derive via `solvedTypeToGo` (the env-aware path),
which re-enters the recursion that closes the cycle.

### What PR 5 must do

Extend `inferTypeFromGoString` (or replace it with a structural
`inferTypeFromGoType :: GoType -> T.Type`) so non-primitive Go
strings round-trip back to a precise `T.Type` instead of the
lossy `T.TVar "_"`.  Shapes needed for Cause-H Step 4:

* `rt.SkyList[T]` → `T.TType list "List" [⟨T⟩]`
* `rt.SkyMaybe[T]` / `rt.SkyResult[E, A]` / `rt.SkyTask[E, A]`
* `rt.SkyDict[K, V]` / `rt.SkySet[T]`
* `rt.T2[A, B]` / `rt.T3[A, B, C]` → `T.TTuple ⟨A⟩ ⟨B⟩ […]`
* `Foo_R[T1, T2]` → parametric record alias lookup
* `func(A) B` → `T.TLambda ⟨A⟩ ⟨B⟩`

Caller side at `lowerTypedLambda` (Compile.hs:8020): feed the
typed `GoType` carried by `paramTys` (currently `[String]`,
post-PR-6 will be `[GoType]`) through `inferTypeFromGoType`
directly — no string parsing.

Strategy C PR 5 + PR 6 (caller signature change) are the gating
prerequisites; only then can PR 7 widen the typed-tuple gate
safely at all six renderer sites.

### What stays shipped

* PR 2 — `solvedTypeToGoTyped` sibling delegate
* PR 3 — `tupleElementSlots` (kills `parseTupleTypeArgs`)

## 2026-06-13 — Smart PR 4 attempt: shared decision via GoType (reverted)

A second, smarter PR 4 attempt was made.  Architecture: a
SHARED `shouldTypedTuple :: T.Type -> Bool` decision used by ALL
six renderer tuple-emission sites.  The decision operates on the
**structural** `T.Type` (not on per-renderer rendered strings),
deriving the answer from the env-free `GoType` ADT via
`solvedTypeToGoTyped` → `isTypedGoElement`.

Theory: this removes BOTH the asymmetry (all sites get the same
answer for the same T.Type) AND the cross-renderer thunk cycle
(the decision uses `mapSkyTypeToGo`, which never calls a legacy
String renderer, so no cross-renderer thunks).

Result: probe-sweep 9/9 GREEN (including probe-C-stdui-msg-typed)
BUT example-sweep 23/26 — three NEW failure classes:

1. **`undefined: rt.SkyDict`** — the PR-1 `GoType.mapSkyTypeToGo`
   for Sky's `Dict` emits `GoNamed "rt.SkyDict" [k, v]`, mirroring
   the legacy `Sky.Generate.Go.Type.typeToGo` shape.  But the
   actual Compile.hs `solvedTypeToGo` emits `"map[string]V"` —
   the runtime has NO `rt.SkyDict` alias.  PR 1's C2 parity test
   (which gates against `typeToGo`) didn't catch this because
   it asserts parity with `typeToGo`, not with the Compile.hs
   renderer.  When the smart `shouldTypedTuple` calls
   `solvedTypeToGoTyped` on a tuple containing `Dict`, the
   resulting `GoType` flows through `tupleElementSlots` →
   `renderGoType` → `exprToGoExpectGo` with the `rt.SkyDict[…]`
   string as the expected slot.  Downstream `exprToGoExpectGo`
   tries to emit `rt.Coerce[rt.SkyDict[…]]` and the validator
   rejects it.

2. **`undefined: Colour`** — bare type-name reference in emitted
   Go.  Likely the same `mapSkyTypeToGo`-vs-`solvedTypeToGo`
   misalignment, but at the user-defined ADT layer (no module
   prefix applied because `defaultMappingContext` lacks the
   env-aware alias-resolution map).

3. **`[]any{…}` vs `[]Std_Ui_Transform_Prop`** — list-element
   asymmetry inside a record alias.  The shared `shouldTypedTuple`
   fixed the OUTER tuple asymmetry but exposed a deeper
   list-of-records asymmetry that the legacy primitive whitelist
   was hiding (it never emitted typed tuples in that path at all).

### Diagnosis

The real architectural gap: **`GoType.mapSkyTypeToGo` and
`Compile.hs:solvedTypeToGo` are TWO DIFFERENT renderers** that
DIVERGE for shapes beyond primitives — Dict, user-defined ADTs,
record aliases.  PR 1's parity test (C2) asserts
`mapSkyTypeToGo ≡ typeToGo` (the env-free Type.hs surface), NOT
`mapSkyTypeToGo ≡ solvedTypeToGo` (the env-aware Compile.hs
production renderer).

For Cause-H Step 4 to land via the GoType ADT path, the
foundation must align:
**`mapSkyTypeToGo` must mirror `solvedTypeToGo`, not `typeToGo`**.
That means:
* Dict emits `map[string]V`, not `rt.SkyDict[K, V]`
* User-defined types consult the env-aware alias map
* Record aliases get the `_R` suffix and parametric instantiations

This is the C8+ "MappingContext widening" phase the Plan agent
flagged as Phase γ.  Until then, `solvedTypeToGoTyped` is only
SAFE to use as a STRUCTURAL probe (e.g., for `shouldTypedTuple`'s
shape-classifier role) — its `renderGoType` output is NOT a
drop-in replacement for `solvedTypeToGo`'s output.

### Net for this iteration

* Smart PR 4 reverted; all 6 tuple sites back on the primitive
  whitelist; sweep returns to 26/26 green.
* `shouldTypedTuple` / `isTypedGoElement` helpers remain compiled
  (unused) — they're the future Cause-H Step 4 gate once the
  GoType.mapSkyTypeToGo realignment lands.
* The diagnosis is the value-add: we now have a precise model of
  WHY incremental widening doesn't work and a precise spec for
  what C8 must do (align mapSkyTypeToGo to solvedTypeToGo).
