## Why naive threading breaks

Inline doc at Compile.hs:7813-7828 documents the architecture:

> Critical for the v0.15.x P37b... ANY downstream code that reads scopeStateRef and forces the value loops on the thunk reading scopeStateRef recursively.

The pattern:
1. A wrapper installs `ctx` via `writeIORef scopeStateRef ctx`.
2. Downstream renderers read `scopeStateRef` lazily — but if reading happens BEFORE WHNF forcing, the lazy thunk recursively reads scopeStateRef again.
3. The `ctxFromIORef` helper + the `forced \`seq\` writeIORef scopeStateRef prev` restore pattern dodge this by forcing WHNF at the snapshot point.

Replacing the IORef with explicit `LowerCtx` parameter passing requires:
* Every reader function to take `LowerCtx` as an explicit argument.
* Every wrapper that today writes the IORef to instead RETURN an updated ctx that flows through subsequent calls.
* The TCO interaction (per pre-mortem lesson 3): `Sky.Build.TailCallOpt` reads `_lc_enclosingTypeParams` via the scopeStateRef snapshot — the threading must reach there.

This is a renderer-pipeline refactor, not a 1.5-session PR.

## Same architectural class as PR-6c + PR-7

All three IORefs share the load-bearing pattern:
* Used to leak state across deeply-nested renderer call stacks where threading would explode.
* Reads/writes happen at well-defined synchronisation points to dodge laziness.
* Test specs depend on the exact write/read ordering for correctness.

The right fix is a single rewrite that introduces explicit ctx threading through the renderer chain. Multiple-PRs each attempting individual defusings cost more time per IORef than the consolidated rewrite would cost for all four together.
