Adversarial grill round 5 rejected the Std.Analytics / Std.Db pool work
because **nine defects introduced at once left both suites green**. Each
gate had been shown able to fail alone, which is a strictly weaker
property than the one that matters. This is the experiment that checks the
stronger one, and — the part a single-mutation check cannot reach —
whether the failures still *discriminate* when all nine are present.

### Per-mutation detail

#### `A1` — the shared-pool sizing collapses to the bare quarter-share, so at <=4 cores the two background caps consume the whole pool and the session store is guaranteed nothing

Touches `runtime-go/rt/db_pool.go`. Alone, it fails:

- `TestTheBackgroundWritersCannotStarveTheSessionStore`
  - pg_embed_sizing_test.go:205: cpus=1: sharing left the session store 0 guaranteed connections out of a pool of 2, where owning a pool outright gave it 2 — sharing must not cost the request path anything
- `TestTheHistoricalSizingViolatesTheProperty`
  - pg_embed_sizing_test.go:177: the historical sizing was known to under-provision at 6 cores, but this gate no longer detects it there
- `TestThePoolSizingFixtureMatchesTheGoArithmetic`
  - pool_sizing_fixture_test.go:84: testdata/db_pool_sizing.tsv no longer matches the Go pool arithmetic.
- `TestTheSharedPoolReservesTelemetrysActualCap`
  - dbshare_pool_test.go:338: with analytics capped at 2 and telemetry at 2, a shared pool of 8 guarantees the session store only 4 connections — it had 8 when it owned a pool outright, so sharing is costing the request path

Still failing with all nine applied: TestTheBackgroundWritersCannotStarveTheSessionStore TestTheHistoricalSizingViolatesTheProperty TestThePoolSizingFixtureMatchesTheGoArithmetic TestTheSharedPoolReservesTelemetrysActualCap 

#### `A2` — `SET LOCAL` becomes a bare `SET`, so the pooled connection reports synchronous_commit = off for the rest of its life and the next borrower's writes are acked before the WAL hits disk

Touches `runtime-go/rt/analytics_writer.go`. Alone, it fails:

- `TestLiveSyncCommitDoesNotLeakToTheNextBorrower`
  - analytics_writer_test.go:668: synchronous_commit = "off" on the pooled connection AFTER the analytics flush — the setting leaked, so the next user of this connection (the app, on a shared pool) has its writes acknowledged before the WAL reaches disk

Still failing with all nine applied: TestLiveSyncCommitDoesNotLeakToTheNextBorrower 

#### `A3` — the consumer's cap is released at BEGIN rather than at COMMIT, so it bounds nothing for a consumer that writes in transactions — which the analytics writer does on every flush

Touches `runtime-go/rt/dbshare/dbshare.go`. Alone, it fails:

- `TestATransactionHoldsItsConsumerSlotUntilItEnds`
  - dbshare_pool_test.go:449: a consumer capped at 2 held 6 transactions open at once against a pool of 6 — a transaction pins its connection for its lifetime, so the cap bounds nothing for a consumer that writes in transactions (which the analytics writer does on every flush)

Still failing with all nine applied: TestATransactionHoldsItsConsumerSlotUntilItEnds 

#### `A6` — the analytics queue is allocated 1024x its documented bound: 352 MB of ring buffer at open

Touches `runtime-go/rt/analytics_writer.go`. Alone, it fails:

- `TestTheProductionQueueHasTheDocumentedBound`

Still failing with all nine applied: TestTheProductionQueueHasTheDocumentedBound 

#### `A7` — the boot-time conf re-tune is deleted, so max_connections is frozen at initdb while the pools re-read the machine on every start

Still failing with all nine applied: TestASecondBootRetunesTheManagedBlock 

#### `A10` — the last consumer drops the pool from the registry without closing it, leaking a pool's worth of PostgreSQL backends per open/close cycle
