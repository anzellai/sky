## TL;DR

The master plan PR-7 estimated 1 session for defusing `globalAnonRecords`. Wide-grep + design review finds:

* The IORef has only **2 active touchpoints** (1 reader + 1 writer) — lesson 3 is satisfied.
* The `MappingContext.mcAliases` field added at PR-4 was *intended* as the replacement channel but is structurally insufficient: mcAliases keys by ALIAS NAME, the IORef keys by STRUCTURAL SHAPE → fields.
* The IORef serves a producer-consumer pattern across PARALLEL renderer passes (`atomicModifyIORef'`); defusing requires either sequentialising the renderers or threading State through the renderer chain.

Same architectural class as PR-6c: the IORef is load-bearing for a structural reason the master plan budget didn't account for. Applying the PR-6 pattern: ship the analysis, defer the structural rewrite to a future PR where it can ride on the renderer-pipeline refactor.

## Why `mcAliases` cannot replace the IORef

The PR-4 doc comment named PR-7 as `mcAliases`'s consumer:

> `mcAliases — Alias declarations from the current module. Consumed by PR-7 (defuse globalAnonRecords IORef — anon-record structural identity reaches the mapper via this field so the IORef can be retired).`

Inspection of both types reveals the design intent was structurally mistaken:

* `mcAliases :: Map String Can.Alias` — keyed by ALIAS NAME (e.g. `"Cfg"`, `"Model"`).
* `globalAnonRecords :: Map String (Map String T.FieldType)` — keyed by SYNTHESISED NAME (e.g. `"Anon_R_name_label__abc123"`) → fields.

These are different namespaces serving different purposes:

* `mcAliases` carries module-declared record-alias decls (the user wrote `type alias Cfg = { ... }`).
* `globalAnonRecords` carries SYNTHESISED struct types for inline record-shaped values (the user wrote `{ name = "Alice", age = 30 }` without an alias).

The PR-4 mcAliases field is correctly populated by `buildMappingContext` — it just doesn't help PR-7's case.

## Architectural class — same as PR-6c

`globalAnonRecords` is a load-bearing producer-consumer IORef. Defusing requires:

1. **Sequential rendering** with a `State` monad threaded through the entire renderer chain. Every `solvedTypeToGo` site becomes `State (Map String (Map String T.FieldType)) String`. Touches ~60+ call sites + the renderer body.
2. **Two-pass approach**: pre-walk the program collecting every TRecord shape, generate the decls, then render. Challenge: renderers can SYNTHESISE new T.Type values (through type substitution), so a pre-pass might miss shapes.
3. **Parallel-pass-local maps merged at end**: each parallel pass maintains its own `Map.Map String ...` and merges at the orchestrator. Requires changing every renderer signature to return both a String AND a contribution to the anon-record set.

All three are bigger than 1 session.

## Carry-forward plan

The right home for this work is the same place PR-6c's residual landed: an architectural refactor of the renderer chain. Calling it `PR-α-renderer-state-threading` (post-Phase α):

* Subsumes `globalAnonRecords` defusing.
* Subsumes line 7313's `globalCurrentDepModule` migration (carried forward from PR-6c).
* Subsumes any other "deep producer-consumer IORef" pattern in the renderer.
* Estimated 3-4 sessions — full Phase β work.

Until then, the IORefs remain. Their READS happen at well-defined synchronisation points (after the renderer's lazy thunks have forced), so the lazy-CAF risk that v0.16.6 #492 documented at line 12417 does NOT apply to `globalAnonRecords` — `generateAnonRecordDecls` is invoked after the renderer chain has completed, so the IORef's contents are deterministic.
