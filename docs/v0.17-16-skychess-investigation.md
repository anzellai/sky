# v0.17 follow-up — 16-skychess pre-existing failure investigation

**Branch:** `feat/v0.17-fully-typed-codegen`
**Status:** root-cause traced but not closed — defensive renderer
fixes shipped, deeper canonicaliser-side fix queued.

## The symptom

@scripts/example-sweep.sh --build-only@ reports 25/26 with
@16-skychess@ as the single failure throughout the v0.17 branch.

Failure at @go build@:

```
./main.go:636: undefined: Colour
./main.go:639:115: undefined: Colour
```

## What's bare in the emitted Go

Two sites in the emitted @Chess.Ai@ functions reference @Colour@
without the @Chess_Piece_@ module prefix:

* @main.go:636@ — the type assertion @any(colour).(Colour)@ inside
  @Chess_Ai_bestMove@.
* @main.go:639@ — the @colour@ parameter of @Chess_Ai_pickBest@'s
  signature.

Other types ARE correctly qualified at the same lines:

* @Chess_Piece_Piece_R@ (record alias) — works.
* @State_Model_R@ (record alias) — works.

So the bug is specific to **Sky-defined unions** (like @Colour@),
not record aliases.

## Tracing the path

@pickBest@ in @Chess.Ai@ is unannotated.  HM infers its parameter
type via @Move.allLegalMoves colour board model@ where
@allLegalMoves : Colour -> Dict Int Piece -> Model -> List (Int, Int)@.

`Chess.Ai` does @import Chess.Piece exposing (..)@.  So @Colour@ is
in scope as bare @Colour@ in the source.

At HM time, the type carried into the renderer for the @colour@
parameter is likely @Can.TType (Canonical "") "Colour" []@ — empty
home + bare name.  The canonicaliser appears to drop the
@Chess.Piece@ module attribution for @Colour@ when it flows
through cross-module type variables.

## Renderer-side defensive fixes (shipped)

To handle the @empty home + bare name@ case, three renderers now
have @unionRecovery@:

1. `typeStrWithAliasesRegBounded` — v0.13 A2 original.
2. `safeReturnTypeFullBounded` — shipped in this branch.
3. `solvedTypeToGoBounded` — shipped in this branch.

The recovery walks @globalUnionNames@ for any @Mod_Name@ entry
whose final underscore-segment equals the bare name; emits the
qualified form.  Confirmed safe (no regression at sweep).

## Why the fixes don't fully close 16-skychess

Some path emits the param sig and the type-assertion at lines
636/639 **without** going through any of the three patched
renderers.  Candidates:

* The `Can.Def name params body` arm in `defToStmts` lowering of
  unannotated helpers — may render param types via a different
  helper.
* The typed lambda lowering for `any(x).(T)` casts inside
  `coerceArg` / `coerceToFieldType`.
* `safeReturnTypePureBounded` (the third renderer family I haven't
  added unionRecovery to — kept conservative pending verification
  that no in-sweep regression follows).

## What's actually breaking

Per the 5-min trace above, the deeper bug is likely in
**canonicalisation** of types from `import M exposing (..)`-imported
types.  Cross-module type flow for an `exposing (..)`-style import
should preserve the module attribution so the renderer's
empty-home recovery isn't load-bearing in the first place.

## Why this is a pre-existing class

@git log --oneline -S "Colour" -- examples/16-skychess/sky-out@ shows
this binary has been on disk for many revisions of the branch.
The renderer-recovery additions made during this v0.17 work
intentionally close the related class @typeStrWithAliasesRegBounded@
handles cleanly — but they don't cover this one.

## Next-iteration action item

1. Identify which renderer emits the bare @Colour@ at lines 636 +
   639 (likely via instrumentation: temporarily prefix every
   union-emission site with a unique trace token).
2. Either:
   * Add @unionRecovery@ to that renderer (the conservative fix), or
   * Fix the canonicaliser to preserve module attribution for
     @exposing (..)@-imported types (the deeper, durable fix).
