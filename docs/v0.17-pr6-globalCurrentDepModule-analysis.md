## Why the IORef was chosen (load-bearing constraint)

Inline doc at Compile.hs:3255-3260:

> We CANNOT eagerly render-and-restore here because the lazy `getCgEnv` CAF caches its first-evaluated value — if the eager render fires before downstream consumers (specDecls, inferred-sigs builders) get to read `getCgEnv`, those readers receive a stale snapshot and the build breaks. The sentinel approach scopes the hint without touching `cgEnv`.

So a naive "add `_cg_currentDepModule :: Maybe String` to CodegenEnv" reintroduces the very bug the sentinels were designed to dodge.

## The reader at line 12417 is already DEGRADED-PATH

Inline doc at Compile.hs:12404-12416 (v0.16.6 #492 + v0.16.7 PR #124 by arthurmaciel):

> derive the defining module from the def's body region, falling back to the render-order IORef hint only when the region has no per-module ledger entry (synthetic / monomorphised regions). Regions are file-unique, so region-based lookup is deterministic regardless of thunk-forcing order. The IORef hint is brittle on its own: it sticks on the FIRST dep, so a later dep's `let encodeOne x = …` reads the first dep's ambiguous per-module entry and degrades to `func(x any)`.

So the IORef at 12417 is already a **fallback for synthetic/monomorphised regions**; the primary path is region-based. Removing the IORef-fallback simply means those rare regions get `Nothing` (no scope hint) — which matches entry-module flat-lookup behaviour, an acceptable degradation.

## The reader at line 7313 is a BINARY ENTRY/DEP GATE

Inline doc at Compile.hs:7301-7310: `isNothing (readIORef globalCurrentDepModule)` decides whether to emit the v0.17 typed `Std_Html_Html_T[Msg]` (entry) or bare `Std_Html_Html` (dep — because dep Go files don't have entry-module types like `Msg` in scope). This is a true entry-vs-dep distinction; threading it requires propagating an entry/dep boolean through the call stack of `solvedTypeToGo`.

## Why PR-6c is deferred (post-PR-6b finding)

Inventory of `solvedTypeToGo` (and its sibling renderers) in `Compile.hs`:

* **One definition**: `solvedTypeToGo :: T.Type -> String` at line 15903, dispatching to `solvedTypeToGoBounded 64 Set.empty`.
* **60+ call sites** scattered across the codegen pipeline (records, aliases, funcs, Maps, anon-records, typed-Anon emission, partial-app wrappers, etc.).
* **Sibling renderers** that share the same body shape: `solvedTypeToGoPreserveTVars`, `solvedTypeToGoBounded`, `solvedTypeToGoTyped`. Each is its own 100+ line function.
* **Line 7313's reader** lives inside `solvedTypeToGoBounded`'s `T.TType _ "Html" [arg]` arm — it's the binary entry-vs-dep flag for typed-Html emission.

The migration shape suggested by the master plan ("thread `Maybe String` through every call") requires either:

1. **Threading every call site**: ~60 call sites, each must know whether they're in entry or dep mode. Most don't — because the lazy-CAF architecture deliberately makes that knowledge a global IORef rather than a thread-through parameter. Each call site would need its own upstream knowledge to thread the parameter correctly. This is a much bigger rewiring than the 1.5-session budget allows.

2. **Adding the parameter while keeping the IORef as fallback**: the new signature accepts `Maybe String`; default `Nothing` consults the IORef. This isn't defusing — just plumbing an alternate API.

3. **Replacing the sentinel-IORef architecture wholesale**: replace the global IORef with a Reader monad or explicit-env pipeline threaded from `generateGoMulti` downward. This is a multi-PR refactor that touches the whole expression-lowering surface, not a single-PR fix.

### What's structurally different about line 7313 vs 12417

Line 12417 (defused at PR-6b):

* Read the IORef as a FALLBACK only when the per-module region ledger missed.
* The region-based primary path covers the dominant case.
* Removing the fallback regresses synthetic-region behaviour to pre-v0.16.6 #492 — accepted minor degradation.

Line 7313 (still on the IORef):

* The IORef IS the primary source of truth for the entry-vs-dep gate.
* No alternative primary path exists — the entry/dep distinction is fundamentally an emission-context fact, not a per-region fact.
* Has no documented brittleness — it's a Bool flag, not a per-dep name; can't "stick on wrong dep" the way 12417 could.
* The line 7313 gate decides ONE cosmetic emission choice (typed `Std_Html_Html_T[Msg]` for entry, bare `Std_Html_Html` for dep) — its impact is contained to that arm.

So unlike 12417, defusing 7313 requires changing the architecture, not just rewiring a fallback. That's outside PR-6's scope as originally budgeted.
