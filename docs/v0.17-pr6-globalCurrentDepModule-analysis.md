## Why the IORef was chosen (load-bearing constraint)

Inline doc at Compile.hs:3255-3260:

> We CANNOT eagerly render-and-restore here because the lazy `getCgEnv` CAF caches its first-evaluated value — if the eager render fires before downstream consumers (specDecls, inferred-sigs builders) get to read `getCgEnv`, those readers receive a stale snapshot and the build breaks. The sentinel approach scopes the hint without touching `cgEnv`.

So a naive "add `_cg_currentDepModule :: Maybe String` to CodegenEnv" reintroduces the very bug the sentinels were designed to dodge.

## The reader at line 12417 is already DEGRADED-PATH

Inline doc at Compile.hs:12404-12416 (v0.16.6 #492 + v0.16.7 PR #124 by arthurmaciel):

> derive the defining module from the def's body region, falling back to the render-order IORef hint only when the region has no per-module ledger entry (synthetic / monomorphised regions). Regions are file-unique, so region-based lookup is deterministic regardless of thunk-forcing order. The IORef hint is brittle on its own: it sticks on the FIRST dep, so a later dep's `let encodeOne x = …` reads the first dep's ambiguous per-module entry and degrades to `func(x any)`.

So the IORef at 12417 is already a **fallback for synthetic/monomorphised regions**; the primary path is region-based. Removing the IORef-fallback simply means those rare regions get `Nothing` (no scope hint) — which matches entry-module flat-lookup behaviour, an acceptable degradation.

## The reader at line 7313 is a BINARY ENTRY/DEP GATE

Inline doc at Compile.hs:7301-7310: `isNothing (readIORef globalCurrentDepModule)` decides whether to emit the v0.17 typed `Std_Html_Html_T[Msg]` (entry) or bare `Std_Html_Html` (dep — because dep Go files don't have entry-module types like `Msg` in scope). This is a true entry-vs-dep distinction; threading it requires propagating an entry/dep boolean through the call stack of `solvedTypeToGo`.

### PR-6b — migrate line 12417 to explicit parameter

Scope: change `defToStmts :: Can.Def -> [GoIr.GoStmt]` to `defToStmts :: Maybe String -> Can.Def -> [GoIr.GoStmt]`, threading the currentDepModule as an explicit `Maybe String` argument from each of the 5 call sites (lines 3796, 8795, 12063, 13805, 13809). Each call site already has access to the dep modName context (or `Nothing` for entry).

* Removes the IORef read at 12417.
* The change is local — no lazy-CAF caching risk because the argument is passed explicitly per-call, not cached at module load.
* Example sweep gate: 26/26 byte-identical (the IORef-fallback was rare; region-based path covers the dominant case).
* Estimated 1 session.

### PR-6c — migrate line 7313 to explicit parameter

Scope: change `solvedTypeToGo :: T.Type -> String` to `solvedTypeToGo :: Maybe String -> T.Type -> String`. The currentDepModule hint propagates through every recursive call inside its body (it's recursive over `T.Type` constructors). Threading is mechanical — every `solvedTypeToGo rec ty` becomes `solvedTypeToGo curMod ty` and the binary entry-vs-dep gate at the `T.TType _ "Html" [arg]` arm reads from the explicit parameter.

* Removes the IORef read at 7313 + the IORef definition + writes.
* Touches every call site of `solvedTypeToGo` in Compile.hs (many — needs careful grep).
* Example sweep gate: byte-identical (the gate was already correct under the IORef; the parameter just makes it explicit).
* Estimated 1.5-2 sessions.

### PR-6d (cleanup) — remove the IORef definition + writes

Once 6b + 6c have migrated both readers, the IORef CAF + the two `writeIORef` sentinels in `generateDeclsForDepScoped` are dead code. Removal is mechanical:

* `globalCurrentDepModule` definition at lines 599-601 — delete.
* `generateDeclsForDepScoped` at 3243-3272 — simplify to just `generateDeclsForDep canMod modPrefix` (the sentinels become no-ops).
* Estimated 0.25 sessions.

## What changed about the master plan

The PR-6 budget of 1.5 sessions was based on the assumption that the IORef could be defused by a single CodegenEnv field addition. The wide-grep + architectural review surfaces the lazy-CAF constraint, which forces the explicit-parameter approach + multi-PR breakdown. This is consistent with the "no-deferral principle" (CLAUDE.md §4) — the work is being done, just split into smaller verifiable steps rather than one risky drop.
