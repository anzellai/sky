# Upgrading from v0.31 to v0.32.0

This page lists every change in v0.32.0 that can affect code or a deploy that
worked on v0.31. Each entry says what changed, the old code, and the new
code.

- **Loud** changes stop the build. The error names the change.
- **Loud at run time** changes compile, and the program then returns an `Err`
  that names the change.
- **Silent** changes compile, but the program behaves differently.

The full story of each change is in `CHANGELOG.md` under v0.32.0. The patch
v0.32.1 adds four loud changes, each marked "(v0.32.1)" below.

## Loud (fails to compile, the error shows the fix)

### New stdlib names

A bare name that two `exposing (..)` imports now both export is `[E1012]`
ambiguous, and the error names both modules. The fix is the qualified name,
or a narrower exposing list.

| New name | Module | Collides with | Write |
|---|---|---|---|
| `toResult` | `Sky.Core.Task` | `Sky.Core.Maybe.toResult` | `Task.toResult`, `Maybe.toResult` |
| `bestEffort`, `unless` | `Sky.Core.Task` | no stdlib name | `Task.bestEffort`, `Task.unless` |

Old code:

```elm
import Sky.Core.Maybe exposing (..)
import Sky.Core.Task exposing (..)

portNumber : Result Error Int
portNumber =
    toResult (Error.invalidInput "no port") (String.toInt raw)
```

New code:

```elm
import Sky.Core.Maybe as Maybe exposing (..)
import Sky.Core.Task exposing (..)

portNumber : Result Error Int
portNumber =
    Maybe.toResult (Error.invalidInput "no port") (String.toInt raw)
```

A project that defined its own `bestEffort` or `unless` (AGENTS.md before
v0.32.0 suggested both) can delete them and call `Task.bestEffort` and
`Task.unless`, which do the same.

### `<-` outside a `let` block is `[E0001]`

`<-` was never valid Sky. Before v0.32.0 it was `[E1014] UNKNOWN OPERATOR`.
It is now the parse error `[E0001]`, whose message says that `<-` is a bind
line and belongs in a `let` block. No program that compiled on v0.31 changes.

### `Std.Db.Decode` has its own `Decoder`

A row decoder (`Std.Db.Decode`) and a JSON decoder (`Sky.Core.Json.Decode`)
were one type to the checker. A row decoder passed to `Decode.decodeString`
compiled and then panicked. Now each module has its own `Decoder`, and the
bare name `Decoder` (written with no import) is the JSON decoder. Mixing them
is `[E2001]`.

Old code:

```elm
import Std.Db.Decode as DbDecode

userDecoder : Decoder User
userDecoder =
    DbDecode.succeed User
        |> DbDecode.andMap (DbDecode.int "id")
```

New code:

```elm
import Std.Db.Decode as DbDecode

userDecoder : DbDecode.Decoder User
userDecoder =
    DbDecode.succeed User
        |> DbDecode.andMap (DbDecode.int "id")
```

`import Std.Db.Decode exposing (Decoder)` also works, when the module does not
write a JSON `Decoder` too.

### The bare `Decoder` is not a `Std.Config` or `Std.Xml.Decode` decoder

The same rule holds for the two other modules that declare a `Decoder`. Code
that wrote a TOML, YAML or XML decoder's type as the bare `Decoder` gets
`[E2001]`. Write the module's own type:

```elm
import Std.Config as Config

dbDecoder : Config.Decoder DbCfg
```

```elm
import Std.Xml.Decode as XmlDecode

entry : XmlDecode.Decoder Entry
```

### `Decoder` under two `exposing (..)` imports

`Sky.Core.Json.Decode`, `Std.Db.Decode` and `Std.Config` each export a
`Decoder`. A module that imports two of them with `exposing (..)` and writes
the bare `Decoder` gets `[E1012]`, which names both modules. Write the
qualified name (`Decode.Decoder`, `DbDecode.Decoder`, `Config.Decoder`), or
use a narrower exposing list.

### A pattern in a parameter or a `let` destructure must match every value

A lambda parameter, a function parameter (top level or in a `let`) and a
`let` destructure have no second branch to take. A pattern there that can fail
is `[E3001]`. Before v0.32.0, `\(Just x) -> x` applied to `Nothing` returned
`0` with no error, and `let (Just x) = m in x` panicked.

These patterns can fail, so they need a `case`: a literal (`0`, `"a"`, `'c'`),
`True` or `False`, a list or cons pattern (`[ x ]`, `x :: rest`), and a
constructor of a type with two or more variants (`Just x`, `Ok v`). These
patterns match every value and stay accepted, also nested: a variable, `_`,
`()`, a record, a tuple, an alias (`as`), and the constructor of a type with
one variant (`type Wrap = Wrap Int`).

Old code:

```elm
first : List Int -> Int
first (x :: _) =
    x
```

New code:

```elm
first : List Int -> Int
first xs =
    case xs of
        x :: _ ->
            x

        [] ->
            0
```

### A type with a bare qualifier must be a type of its home (v0.32.1)

A qualifier that no import binds (`Time`, `Dict`, `Process`) reaches its
import-free home module: `Time` is `Sky.Core.Time`. Before v0.32.1 a type name
behind such a qualifier was not checked, so `Time.Parts` with no import named
the `Std.Time` record. It is now `[E1001]`, and the message names the import:

```text
`Time` has no type `Parts`. `Parts` is in `Std.Time`: add `import Std.Time as Time`
```

Old code:

```elm
hourOf : Time.Parts -> Int
hourOf p =
    p.hour
```

New code:

```elm
import Std.Time as Time

hourOf : Time.Parts -> Int
hourOf p =
    p.hour
```

A type the home module exports (`Process.Command`) and a kernel-backed type
the home itself uses (`Dict.Dict`, `Set.Set`, `Cmd.Cmd`, `Task.Task`) stay
valid with no import.

### An unknown type behind a bare qualifier is `[E1001]` (v0.32.1)

A type name that the qualifier's home does not have, and that no other stdlib
module of that name exports, was accepted before v0.32.1 (`Time.NoSuchType`,
`Dict.Dictionary String Int`). It is now `[E1001]` "`Dict` has no type
`Dictionary`". The fix is the real type name (`Dict.Dict String Int`).

### A type behind the alias of your own module must be one it exports (v0.32.1)

Under `import Lib.Db as L`, every `L.T` must be a type that `Lib.Db` exports.
Before v0.32.1 the built-in type names `Decoder`, `Value`, `Attribute`,
`Handler`, `Middleware`, `Session`, `Store`, `Route`, `VNode`, `Request`,
`Response`, `Cmd`, `Sub`, `Db` and `Error` were accepted behind ANY alias,
also when the module did not export them, and the type checker then picked a
type of that name by its bare name. The same held for any type behind an alias
whose name is also a kernel qualifier (`import Lib.Db as Db`, then
`Db.Missing`). Each is now `[E1001]`:

```text
Undefined name: L.Error. The module `Lib.Db` does not export a type `Error`
(`Error` is a built-in type: write `Error` with no qualifier).
```

Old code:

```elm
import Lib.Db as L

save : L.Conn -> Task L.Error ()
```

New code:

```elm
import Lib.Db as L

save : L.Conn -> Task Error ()
```

A type the module declares and exposes (`L.Conn`), and a type it re-exports by
listing it in its `exposing` clause (`module Lib.Db exposing (Conn, Db)` with
`import Std.Db exposing (Db)`), stay valid. A name close to an exported type
gets a did-you-mean (`L.Con`: did you mean `L.Conn`?), and a type of exactly
one stdlib module names that module.
Under an import of a standard library module the built-in names stay valid
(`Db.Db` under `import Std.Db as Db`).

### A qualified kernel type is never your own type of the same name (v0.32.1)

A qualified kernel type with no `.sky` declaration (`JsonEnc.Value`,
`Dict.Dict`) is the kernel type. Before v0.32.1 a type of your module with the
same bare name took its place: with `type alias Value = { n : Int }` in the
module, `f : JsonEnc.Value -> Int` with `f v = v.n` passed `sky check`. It is
now `[E2001]` (a JSON value has no field `n`). Rename your type, or write it
unqualified where you mean it.

The same holds for the values the stdlib functions give. Before v0.32.1 the
bare `Value` in `JsonEnc.int : Int -> Value` was read as your
`type alias Value`, so `(JsonEnc.int 1).n` passed `sky check`. It is now
`[E2001]`. Code that uses the JSON value as a JSON value is not changed.

## Loud at CI (`sky fmt --check` reports files that used to pass)

### Run `sky fmt` once after the upgrade

After upgrading to v0.32.x, run `sky fmt` once on a project whose CI runs
`sky fmt --check`: v0.32.0's formatter formats every declaration it can and
keeps only a declaration whose comment it cannot place, where v0.31 left the
whole file unformatted, so `--check` reports files that used to pass.

```bash
sky fmt src/*.sky         # each file that CI checks
git diff                  # layout only, no change of meaning
```

## Warned in v0.32.1, `[E1001]` in the next minor

### A type that the imported stdlib module does not export

A qualified type under an import of a standard library module must be a type
that the module exports. `Std.Ui` does not export `Html`, so `Ui.Html` under
`import Std.Ui as Ui` names no type of `Std.Ui`. v0.32.x still accepts it, as a
type with no module, which the type checker matches with any type of that
name. `sky check` warns and names the module that exports a type of that name:

```text
warning: `Html` is not exported by `Std.Ui`: use `Html.Html` from `Std.Html`.
This is accepted in v0.32 and is [E1001] in the next minor version.
```

Write the exported name and import its module:

```elm
import Std.Html as Html

view : Model -> Html.Html Msg
```

The next minor version reports the old form as `[E1001]`.

Since v0.32.1 such a name means the ONE stdlib type of that name when exactly
one stdlib module exports it (`Ui.Html` is `Std.Html`'s `Html`), and no other
type. Before, it matched any type of that name, also one of your own module.
A name no stdlib module exports, or several do, is not checked against any
type until you write the exported name.

## New in v0.32.0 (not breaking)

### Bind lines in `let` blocks

`p <- e` as a line of a `let` block runs `e` and binds its result to `p` for
the rest of the block. It replaces a chain of nested `andThen` lambdas.
Nothing that compiled before changes meaning: `<-` was not valid Sky.

Old code:

```elm
recordVisit : Ref Stats -> Task Error Stats
recordVisit ref =
    Sync.get ref
        |> Task.andThen
               (\stats ->
                   Time.now ()
                       |> Task.andThen
                              (\now ->
                                  let
                                      next =
                                          { stats | visits = stats.visits + 1, lastSeen = now }
                                  in
                                      Sync.set next ref
                                          |> Task.andThen (\_ -> Task.succeed next)))
```

New code:

```elm
recordVisit : Ref Stats -> Task Error Stats
recordVisit ref =
    let
        stats <- Sync.get ref
        now <- Time.now ()
        next = { stats | visits = stats.visits + 1, lastSeen = now }
        _ <- Sync.set next ref
    in
        Task.succeed next
```

The rules and the errors are in `docs/language/syntax.md` ("Bind lines"),
`docs/errors/E2015-bind-needs-a-type.md` and
`docs/errors/E2016-no-andthen.md`.
